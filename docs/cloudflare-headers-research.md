# 347movies — Cloudflare Pages security-header application (research)

**Researched 2026-08-16.** Question: how do `public/_headers` rules, the root
`functions/_middleware.ts`, and Pages' 404 handling actually interact on this site — and does
any response class fall through without the hardened security headers? Method: primary sources
only (official Cloudflare Pages docs for [Headers](https://developers.cloudflare.com/pages/configuration/headers/)
and [Middleware](https://developers.cloudflare.com/pages/functions/middleware/)), then empirical
verification of every response class against the live site (curl HEAD/GET on `347movies.pages.dev`).

## Findings

### 1. `_headers` rules apply to static asset responses ONLY — never to Pages Functions responses

The official docs state this explicitly: *"Custom headers defined in the `_headers` file are not
applied to responses generated by Pages Functions, even if the request URL matches a rule defined
in `_headers`."* The docs' recommendation matches this site's existing design: attach security
headers for function routes *in the function code* (here, the root middleware).

**Empirically confirmed.** `/api/health` (a function route) carries the full security header set
(CSP, HSTS, nosniff, XFO, Referrer-Policy, Permissions-Policy) plus `X-Robots-Tag: noindex`. Since
`_headers` cannot apply to function responses, every one of those headers can only have come from
`functions/_middleware.ts`. The current split — `_headers` for static assets, middleware for
function routes — is exactly the architecture the docs prescribe.

### 2. Root middleware runs in front of static files too — both layers, no conflict

The Middleware docs: *"If you want to run a middleware on your entire application, including in
front of static files, create a `functions/_middleware.js` file."* So a static asset response is
subject to BOTH the `_headers` rules and the middleware. No conflict occurs here because the
middleware only fills gaps (`if (!response.headers.has(name))`), and both sources carry the same
values.

**Empirically confirmed.** `/` and `/css/style.css` (static) and `/api/health` (function) all serve
the identical CSP/HSTS/nosniff/XFO set — one copy each, no duplicates, no overrides.

### 3. 404 handling: in-page meta is the real noindex, not the `/404.html` `_headers` rule

Three distinct surfaces were probed:

| Request | Status | Security headers | X-Robots-Tag |
|---|---|---|---|
| `/404.html` (literal) | **308 → `/404`** | full set | `noindex` (from the `/404.html` rule) |
| `/404` | 200 (custom 404 page) | full set | **absent** |
| any unknown route (e.g. `/definitely-not-a-page-xyz`) | 404 (custom 404 page) | full set | **absent** |

The `public/_headers` rule `X-Robots-Tag: noindex` on `/404.html` is effectively **dead weight**:
the literal `/404.html` URL 308-redirects to `/404` before a crawler can read the header, and the
unknown-route 404 — the surface that actually needs noindex — never matches a `/404.html` rule
(rules match the *requested* URL, not the served 404 page). The noindex protection that actually
works on the unknown-route 404 and on `/404` is the in-page
`<meta name="robots" content="noindex, follow">` in the custom page body.

This is **not a vulnerability** — meta-robots noindex is honored by all major engines, and the
404 carries the full security header set (CSP prevents any injection into the page regardless).
It is worth documenting so nobody "fixes" the 404 noindex by editing the `/404.html`
`_headers` rule expecting it to cover unknown routes — it never will.

**Follow-up fix (deploy #57 = 75136642):** header-level noindex on every 404 is now real — the
root middleware adds `X-Robots-Tag: noindex` to any 404 response (`functions/_middleware.ts`).
Because the middleware wraps *all* requests — including static-asset 404s that never match a
`_headers` rule — this covers every 404 origin with one line, and the in-page meta stays as
defense in depth. Negative-proven and smoke-guarded.

## Guard gap found and closed

The smoke suite's security-header section only asserted headers on `/` — a **static** asset, which
is covered by `_headers` even if the middleware headers were ever removed. Nothing asserted that a
**function route** carries the security headers, which only middleware can supply. A regression
that dropped the middleware's security headers would have sailed through the smoke suite green
while `/api/*` and `/movie/*` lost their CSP. Per the project's guard discipline (every invariant
gets a negative-provable guard), `scripts/smoke.mjs` now also asserts:

- the full security header set on `/api/health` (a function route — middleware-only path), and
- the header-level `X-Robots-Tag: noindex` on the unknown-route 404 (deploy #57) plus the
  in-page noindex meta (defense in depth).

All were negative-proven (removing the middleware headers / the 404 noindex block / the meta fails
the suite) before the change was kept. Smoke: 113 → 122.

## Verification

- Primary docs read in full: Cloudflare Pages *Headers* and *Middleware* pages (cited above).
- Live probes on `https://347movies.pages.dev`: `/`, `/css/style.css`, `/api/health`, `/404.html`,
  `/404`, `/definitely-not-a-page-xyz` — status, header set, and 404 body all captured above.
- Extended surface sweep (follow-up pass): `/movie/it-1927` (SSR), `/sitemap.xml`, `HEAD` on
  `/api/health`, and an edge-cache hit (`cf-cache-status: HIT`) — **all carry the full security
  header set**; the cache hit proves the middleware wraps cached responses too (the edge cache
  stores the pre-middleware response, but the middleware re-adds headers on every request).
- Smoke suite extended (113 → 122), dev smoke green, canonical smoke green against production
  (deploy #57 = 75136642).
